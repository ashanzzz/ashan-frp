# Ashan FRP 变更安全合同（AI 与人工维护者）

> 状态：**强制执行**。本文件与根目录 `AGENTS.md` 同等约束所有修改 `frp-backend/`、嵌入式 UI、认证、凭据、Provider 或运行时流程的维护者。
>
> 目的：每次修一个问题时，保住已经完成并验证过的能力；禁止以猜测、静态构建通过或“看起来更简单”为理由移除、改写或破坏既有行为。

## 1. 先读后改：事实源顺序

动手前必须按顺序阅读：

1. 根目录 `AGENTS.md`。
2. `docs/project-map.md`（当前产品边界、成熟度、目录责任）。
3. 与本次改动直接相关的 `docs/specs/ashan-frp/design/*.md`。
4. `CHANGELOG.md`（最近已经实现且不得误删的行为）。
5. 目标文件及其现有单元、集成、浏览器测试。

如果文档、测试与代码相互矛盾：**停止实现**，记录冲突，先由项目所有者或明确设计文档裁决；禁止任选一个版本静默覆盖另一个版本。

## 2. 不变量清单

### 2.1 本地认证边界

- `/api/v1` 的受保护请求在到达 Cloudflare、ChmlFrp、OnePanel、FRPC 或数据库业务处理前，可能被本地 session/auth middleware 拒绝。
- 本地 `401 UNAUTHORIZED` 必须被 UI 识别为“需要重新登录”；不得显示为服务商错误，也不得显示为操作成功。
- 除 public session probe 和登录接口外，嵌入式 UI 的受保护请求必须通过唯一的认证请求包装器。新增裸 `fetch('/api/v1/...')` 是回归。
- 请求失败时，状态、缓存、success notice、列表和统计数据不得假设操作已成功。

### 2.2 Provider 认证语义

- Cloudflare API Token 与 Global API Key 是显式的不同模式；Global API Key 必须使用 Email + Key，API Token 使用 Bearer Token。不得以输入框是否填写或字符串前缀作为唯一事实。
- ChmlFrp 用户名/密码与 API/OAuth Token 是显式的不同模式；客户端构造器、持久化元数据和调用点必须能表明选择的是哪一种模式。
- **禁止**把 `username, secret` 这类非类型化字符串参数通过“是否为空”“长得像 Token”等规则猜测认证方式。
- 新保存的 ChmlFrp Token 必须通过 `/userinfo` 得到真实当前账户；旧的 `token`、`oauth2_user` 或 Token 本身不得显示为账号。

### 2.3 凭据与设置事务

- 已认证单管理员的 Settings API/UI 可以完整明文显示 Cloudflare 与 ChmlFrp 当前密钥；这是一项批准的个人项目产品决策，不得擅自掩码或删除回显。
- 明文只允许在已认证 Settings 响应和明确批准的成功配置响应中出现，并带 `Cache-Control: no-store`；绝不进入日志、审计、错误、URL、浏览器持久化或未认证响应。
- 任何需要验证 Provider 凭据的设置保存必须遵循：**验证全部输入 → 单一事务持久化 → 返回成功**。
- Provider 验证或任一数据库写入失败时，普通设置、integration metadata 与凭据必须全部保持原值；禁止部分保存。

### 2.4 已完成行为保护

- 不得为满足单一新需求删除 OAuth、Cloudflare Zone 选择、全局 Key 支持、既有 UI 交互、FRPC 生命周期或后台同步能力。
- 若必须改变一个已验证行为，PR 必须列出：旧行为、改变理由、迁移策略、受影响调用点、替代验证和回滚路径。
- 删除能力必须有项目所有者的明确指令；无指令时优先修复根因，不添加 silent fallback，也不保留未定义的兼容猜测。

## 3. 每次改动的必经流程

### A. 修改前：建立行为清单

在 issue、计划或 PR 描述中写出：

- 本次目标和明确的非目标。
- 受影响的 API、UI 操作、数据库记录、worker 调用点和 Provider 模式。
- 必须保持的现有行为，逐项指向测试或设计文档。
- 失败场景：未登录、无权限、无效凭据、网络失败、数据库失败、旧数据。

### B. 测试先行：新旧行为同时锁定

每一项行为修改至少包含：

1. 一个新需求的成功测试。
2. 一个失败边界测试。
3. 一个防止旧能力消失的回归测试。
4. API/UI 变更时，一个真实 HTTP 或 mock Provider 集成测试。
5. UI 交互变更时，一个真实浏览器测试。

禁止用“前端 bundle 包含字符串”“单个函数单测通过”代替 session、路由、Provider 或浏览器验证。

### C. 实现：小范围、显式、可审计

- 一个 PR 只做一个连续问题域；认证模式重构、UI 重排和无关清理不得混在同一个提交。
- 新增 Provider/认证分支使用类型、枚举、独立构造器或显式字段表达语义。
- 被验证的输入在所有副作用之前处理；多记录写入使用 repository 事务。
- 任何 Provider 请求都不得记录完整 Token、密码、Cookie、Authorization header 或原始 body。

### D. 验收：分层证据

按改动范围执行并保留输出：

```bash
cd frp-backend
go test ./...
go vet ./...
node --test internal/web/app.test.mjs
npm run build
```

若涉及 UI/嵌入式产物，还必须：

1. 用新 build 重新编译 Go 二进制。
2. 启动隔离数据目录的临时实例。
3. 对未登录和已登录路径做真实 HTTP 验证。
4. 用真实浏览器完成关键流程。

浏览器服务不可用时，只能报告“浏览器验证被阻断”；不得声称 UI 已验证或合并 UI 行为改动。应先恢复浏览器服务、改用已批准的浏览器测试环境，或等待项目所有者决定。

### E. 合并前：双重审查

- **规格审查**：是否完整满足目标、非目标和不变量？
- **回归审查**：是否错误改变认证模式、绕过认证包装器、产生部分写入、删除已有交互或泄露凭据？
- 两项审查都通过，且 CI 全绿，才能合并。
