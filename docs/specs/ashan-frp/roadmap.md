# ashan-frp 交付路线图

> 作用：把已验证的架构结论转换为可执行的交付顺序，避免把“计划”写进已定稿的架构正文。
> 范围：仅描述下一阶段的实施顺序、依赖、风险和验收方式；不重复架构总览中的设计结论。
> 约束：本文件是路线图，不是实现细节说明书；若后续出现架构调整，应先更新对应 design 文档，再同步修订这里。
> 约束：所有实施都以 Docker / Compose 可部署为默认前提；Windows 本机环境只能作为开发辅助，不作为生产运行假设。


## 1. 路线图目标

本轮路线图的目标是把 `ashan-frp` 从“已验证的架构与设计”推进到“可按阶段落地的交付计划”。

核心目标：

- 保持 `docs/specs/ashan-frp/architecture.md` 只包含已验证事实与稳定结论。
- 将未完成的工作拆成可独立验收的阶段。
- 明确每个阶段的输入、输出、风险和完成标准。
- 让团队在不修改架构正文的前提下持续跟踪实施进度。

## 2. 当前基线

从现有文档可以确认：

- 系统已经收敛为 Go 单体交付形态，前端由 Go 二进制内嵌提供。
- API、SSE、状态存储、Job Runner、FRPC runtime manager 已经形成稳定的职责分层。
- 架构正文、数据映射、UI 布局、运行时模型等设计卡片已经存在。
- 仍有若干开放问题，需要在实现过程中逐项验证，而不是一次性写死。

因此，这份路线图不重新讨论“是否做”，只安排“先做什么、后做什么”。

## 3. 交付原则

1. **先稳定事实源，再扩展功能**
   - 先保证本地状态、任务执行和观测数据的闭环正确。
   - 再扩展更复杂的同步、调度和外部适配。

2. **先单点闭环，再横向扩展**
   - 先完成一个资源链路的完整可用路径。
   - 再扩展到更多资源类型、更多上游实例或更复杂的运维动作。

3. **先验证可观测，再追求自动化**
   - 所有关键动作必须能追踪、回放、排查。
   - 自动化能力建立在可解释的 job/event/audit 之上。

4. **先文档分层，再实施分层**
   - 架构正文保持稳定。
   - 路线图承载阶段性计划。
   - 具体实现细节放到对应模块与代码注释中。

## 4. 建议的阶段划分

### Phase 0：基线确认

**目标**：确认当前代码与设计文档仍然一致，避免在错误前提上推进。

**工作项**：

- 对照 `architecture.md` 与当前代码，确认单体 Go 交付形态仍成立。
- 对照 `design/backend-schema.md`、`design/api-payload-mapping.md`，确认核心数据对象没有发生未记录漂移。
- 对照 `design/frontend-ui.md` 与嵌入式 UI 现状，确认页面地图与交互约束仍匹配。

**完成标准**：

- 架构正文无需大改。
- 仅补充必要的注记或开放问题。
- 没有发现需要立即重写架构层次的偏差。

**风险**：

- 如果实现代码已偏离设计太多，后续阶段必须先修正基线，再继续。

---

### Phase 1：核心链路稳定化

**目标**：让最关键的控制面链路稳定、可追踪、可排障。

**工作项**：

- 保证 API → job → runner → state 回写的最小闭环可用。
- 统一 job 状态、事件记录和错误返回的语义。
- 确认 SSE 事件流能稳定承载前端实时刷新需求。
- 处理本地状态文件或持久化层的基本一致性问题。

**完成标准**：

- 关键操作都有明确的 job 记录和事件轨迹。
- 失败场景可复现、可定位、可恢复。
- 前端能够依赖 SSE 或轮询拿到一致视图。

**风险**：

- 若 job 状态机与事件模型定义不统一，会导致前端与运维排障体验割裂。

---

### Phase 2：资源管理面补齐

**目标**：把节点、隧道、站点映射和设置等资源管理体验补完整。

**工作项**：

- 完善资源列表、详情、编辑和动作入口。
- 确认各资源对象与后台状态的映射关系。
- 处理按钮级操作与异步任务之间的交互。
- 补齐必要的错误提示和确认流程。

**完成标准**：

- 资源管理页面能支撑日常操作。
- 资源状态、任务状态和后台事实之间没有歧义。
- 用户能看懂每一步动作是否已提交、执行中或失败。

**风险**：

- 如果动作模型过度复杂，UI 会先于后台逻辑暴露不一致问题。

---

### Phase 3：外部适配与同步增强

**目标**：在稳定闭环之上，增强与 1Panel、Docker、FRP、DNS 等外部系统的适配能力。

**工作项**：

- 完善 adapter 层的 DTO 归一化与错误处理。
- 逐步增强同步、对账和漂移检测能力。
- 处理外部系统版本变化与接口漂移。
- 为多实例或多上游场景保留扩展点。

**完成标准**：

- 外部 API 的变化主要影响 adapter 层，而不是整个系统。
- 同步失败不会破坏本地事实源。
- 新增外部依赖时，有明确接入边界。

**风险**：

- 外部系统不稳定时，必须避免把远端响应直接当作本地真理。

---

### Phase 4：体验打磨与运维增强

**目标**：在功能可用后，优化可用性、可维护性和运维体验。

**工作项**：

- 优化仪表盘、日志、任务队列和设置页面。
- 提高错误信息的可读性和可操作性。
- 增加常见故障的引导与恢复提示。
- 处理文档与实际行为的长期同步。

**完成标准**：

- 日常操作无需频繁查文档即可完成。
- 常见错误有明确处理路径。
- 新增功能不会破坏已有页面结构和操作心智。

## 5. 决策门（Go / No-Go）

每一阶段进入下一阶段前，至少确认以下问题：

- 当前阶段的验收标准是否已经满足？
- 是否存在未记录的架构偏差？
- 是否需要先更新对应 design 文档？
- 新需求是否会影响已验证的事实源定义？

如果任一答案为“是”，先回到对应 design 文档或基线校准，不要直接往下叠加功能。

## 6. 文档分工

为了避免文档职责混淆，建议保持以下边界：

- `architecture.md`
  - 只放已验证的系统总览、边界、原则和稳定权衡。

- `design/*.md`
  - 只放具体领域设计、映射、布局、模型和结构说明。

- `roadmap.md`（本文件）
  - 只放分阶段实施顺序、里程碑、风险和验收门槛。

- 代码与测试
  - 承载实际行为，不把实施计划写回架构正文。

## 7. 后续维护建议

- 若某阶段完成且不再代表未来计划，应将其从“路线图”转为“已交付记录”。
- 若出现新的大范围方向变化，应新开一份路线图修订，而不是回写架构总览。
- 若某个开放问题被验证，应迁移到对应设计卡片或架构附录，而不是长期挂在路线图中。

## 8. 结论

本次审查的结果是：**适合写独立路线图，不适合把计划内容并入架构正文**。

原因很简单：

- 架构正文已经承担“已验证事实”的职责。
- 路线图承担“下一步怎么落地”的职责。
- 两者混写会让团队难以判断哪些是稳定结论，哪些只是计划。

因此，后续所有实施推进都应以本文件为路线图入口，以 `architecture.md` 和对应 `design/*.md` 为事实依据。
