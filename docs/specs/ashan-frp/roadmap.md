# ashan-frp 交付路线图

> 作用：把已验证的架构结论转换为可执行的交付顺序，避免把“计划”写进已定稿的架构正文。
> 范围：仅描述下一阶段的实施顺序、依赖、风险和验收方式；不重复架构总览中的设计结论。
> 约束：本文件是路线图，不是实现细节说明书；若后续出现架构调整，应先更新对应 design 文档，再同步修订这里。
> 约束：所有实施都以 Docker / Compose 可部署为默认前提；Windows 本机环境只能作为开发辅助，不作为生产运行假设。


## 1. 路线图目标

本轮路线图的目标是把 `ashan-frp` 从“已验证的架构与设计”推进到“可按阶段落地的交付计划”。

核心目标：

- 保持 `docs/specs/ashan-frp/architecture.md` 只包含已验证事实与稳定结论。
- 将未完成的工作拆成可独立验收的阶段。
- 明确每个阶段的输入、输出、风险和完成标准。
- 让团队在不修改架构正文的前提下持续跟踪实施进度。

## 2. 当前基线

从现有文档可以确认：

- 系统已经收敛为 Go 单体交付形态，前端由 Go 二进制内嵌提供。
- API、SSE、状态存储、Job Runner、FRPC runtime manager 已经形成稳定的职责分层。
- 架构正文、数据映射、UI 布局、运行时模型等设计卡片已经存在。
- 仍有若干开放问题，需要在实现过程中逐项验证，而不是一次性写死。

因此，这份路线图不重新讨论“是否做”，只安排“先做什么、后做什么”。

## 3. 交付原则

1. **先稳定事实源，再扩展功能**
   - 先保证本地状态、任务执行和观测数据的闭环正确。
   - 再扩展更复杂的同步、调度和外部适配。

2. **先单点闭环，再横向扩展**
   - 先完成一个资源链路的完整可用路径。
   - 再扩展到更多资源类型、更多上游实例或更复杂的运维动作。

3. **先验证可观测，再追求自动化**
   - 所有关键动作必须能追踪、回放、排查。
   - 自动化能力建立在可解释的 job/event/audit 之上。

4. **先文档分层，再实施分层**
   - 架构正文保持稳定。
   - 路线图承载阶段性计划。
   - 具体实现细节放到对应模块与代码注释中。

## 4. 交付与调试阶段划分

### 阶段 1：总控台 (Control Center) 完善与调试

**目标**：打磨管理界面的核心控制台，确保系统健康指标、4层健康检查、隧道映射矩阵、快速拨码与一键 Auto-provision 功能100%可调试、无盲点。

**核心交付与验证**：
- 4层健康检查与指标仪表盘（Go Runtime, SQLite, FRPC Supervisor, External Providers）。
- 隧道映射矩阵 (Tunnel Matrix) 与本地端口/域名一键联动。
- 设置中心与凭据遮蔽保护（Token Masking/Revision）。

---

### 阶段 2：Cloudflare 集成与 DNS / Tunnel 调度

**目标**：实现 Cloudflare API Token 鉴权、Zones 列表管理、DNS 记录 CRUD 与 Tunnel 绑定。

**核心交付与验证**：
- Cloudflare Token 校验与凭据无秘钥保存。
- A/AAAA/CNAME/TXT/MX/CAA 记录的高效增删改查与搜索。
- DNS 记录与 Cloudflare Tunnel 自动标注关联及状态对账。

---

### 阶段 3：ChmlFrp 外部 Provider 深度适配

**目标**：接通 ChmlFrp 映射与隧道管理，支持映射同步、节点拉取与配置注入。

**核心交付与验证**：
- ChmlFrp 鉴权与第三方 API 适配层 (Adapter)。
- ChmlFrp 节点在线状态拉取与隧道属性归一化。
- 隧道配置向本地 FRPC 运行参数转换渲染。

---

### 阶段 4：本地内置 FRPC 进程生命周期与控制

**目标**：在 Go 单体服务内实现真正的 FRPC 进程生命周期托管、配置热重载与实时日志采集。

**核心交付与验证**：
- FRPC 进程 Supervisor（启动、优雅停止、崩溃自动重启）。
- `frpc.ini` / `frpc.toml` 配置文件渲染与磁盘持久化。
- FRPC 运行日志/错误输出实时捕获并送入 SSE / 审计视图。

## 5. 决策门（Go / No-Go）

每一阶段进入下一阶段前，至少确认以下问题：

- 当前阶段的验收标准是否已经满足？
- 是否存在未记录的架构偏差？
- 是否需要先更新对应 design 文档？
- 新需求是否会影响已验证的事实源定义？

如果任一答案为“是”，先回到对应 design 文档或基线校准，不要直接往下叠加功能。

## 6. 文档分工

为了避免文档职责混淆，建议保持以下边界：

- `architecture.md`
  - 只放已验证的系统总览、边界、原则和稳定权衡。

- `design/*.md`
  - 只放具体领域设计、映射、布局、模型和结构说明。

- `roadmap.md`（本文件）
  - 只放分阶段实施顺序、里程碑、风险和验收门槛。

- 代码与测试
  - 承载实际行为，不把实施计划写回架构正文。

## 7. 后续维护建议

- 若某阶段完成且不再代表未来计划，应将其从“路线图”转为“已交付记录”。
- 若出现新的大范围方向变化，应新开一份路线图修订，而不是回写架构总览。
- 若某个开放问题被验证，应迁移到对应设计卡片或架构附录，而不是长期挂在路线图中。

## 8. 结论

本次审查的结果是：**适合写独立路线图，不适合把计划内容并入架构正文**。

原因很简单：

- 架构正文已经承担“已验证事实”的职责。
- 路线图承担“下一步怎么落地”的职责。
- 两者混写会让团队难以判断哪些是稳定结论，哪些只是计划。

因此，后续所有实施推进都应以本文件为路线图入口，以 `architecture.md` 和对应 `design/*.md` 为事实依据。
